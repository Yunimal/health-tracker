# 분석 설계 — "결과 ← 원인" 축

현재 대시보드는 "카테고리별로 얼마나 기록했나"를 보여준다. 그건 **저장 구조**지 사용자의
**질문 구조**가 아니다. 사용자의 질문은 이런 형태다:

> "수면이 나빴던 날은 뭐가 달랐나?"

이 문서는 그 질문에 답하기 위한 계산부(`src/lib/analysis/`)의 설계다. 화면은 4단계에서
이 함수들을 쓴다.

```
outcomes.ts   결과 레지스트리 (무엇을 "결과"로 볼지 + 좋음/나쁨 구간)
inputs.ts     원인 후보 자동 추출 (데이터에서 뽑는다 — 하드코딩 금지)
compare.ts    좋은 날/나쁜 날 비교 (단순 빈도만)
```

## 결과를 새로 추가하는 방법

`src/lib/analysis/outcomes.ts` 의 `OUTCOMES` 배열에 **한 줄(객체 하나)** 추가하면 끝이다.
화면·계산 코드는 고치지 않는다. 두 종류가 있다.

**숫자 필드가 있는 결과 (`scale`)** — 값의 구간으로 좋음/나쁨을 가른다.

```ts
{
  kind: "scale",
  id: "sleep_quality",
  label: "수면의 질",
  category: "sleep",
  valuePath: "quality",          // payload.quality
  scale: { min: 1, max: 5 },
  direction: "high_good",         // high_good | low_good | mid_good
  goodRange: [4, 5],
  badRange: [1, 2],               // mid_good 이면 [[1,2],[6,7]] 처럼 양쪽
  lookbackHours: 18,
}
```

**있었나/없었나로 보는 결과 (`presence`)** — 발생 자체가 결과다.

```ts
{
  kind: "presence",
  id: "craving",
  label: "음식 갈망(craving)",
  category: "appetite",
  match: (p) => (p as { kind?: unknown }).kind === "craving",
  lookbackHours: 12,
}
```

- `direction` 은 화면에서 좋은 쪽 방향을 표시할 때만 쓴다(계산에는 goodRange/badRange 만 쓴다).
- `mid_good` 은 양 끝이 나쁜 경우다(브리스톨 1·7 이 나쁘고 4 가 좋음). `badRange` 를 구간 배열로 준다.
- 값이 good/bad 어디에도 안 들면 **middle**(중간)이며 비교에서 빠진다 — 좋았다고도 나빴다고도
  할 수 없는 날이다. middle 은 unknown(기록 없음)과 다르다.

## lookback 값을 어떻게 정했나

`lookbackHours` 는 **원인 후보를 결과 시점 기준 몇 시간 전까지 볼지**다. 인과를 증명하는
값이 아니라, 결과 옆에 나란히 놓고 볼 입력의 시간 창(window) 크기일 뿐이다. 넓으면 무관한
것이 섞이고, 좁으면 전날 입력을 놓친다.

| 결과 | lookback | 근거 |
|---|---|---|
| sleep_quality | 18h | 취침 시각 기준 그날 아침(카페인·운동)부터 담기. 24h 면 전날 취침과 겹쳐 이중 계산, 12h 면 오전 누락 |
| bowel | 36h | 배변은 전날(때론 그 전날 저녁) 먹은 것 영향이 크다(장 통과 시간 하루 안팎). 24h 는 전날 아침·점심이 잘림 |
| mood | 24h | 그날의 수면·식사·활동·사건 전반의 영향을 하루 창으로 |
| menstrual_pain | 24h | 통증 관찰일 기준 전날의 활동·식사·수면을 함께 |
| craving | 12h | 직전 반나절의 허기·스트레스·수면 부족과 가깝게. 하루 전체면 아침 입력까지 섞임 |
| digestion | 24h | 그날(과 전날 저녁) 먹은 것과 연결해 보므로 하루 |

창(window)의 **끝(anchor)** 은:
- `scale` — 그날 결과 이벤트의 가장 늦은 관찰 시각(예: 수면을 아침에 기록하면 그 시각).
- `presence` — 그날의 끝(23:59). 좋은 날엔 기준이 될 이벤트가 없어, good/bad 창을 대칭으로
  두기 위해 양쪽 모두 그날 끝으로 통일한다. (bad 날의 매칭 이벤트 시각을 쓰면 창 위치가
  good 날과 어긋나 편향이 생긴다 — 작은 표본에서 이 편향이 더 해롭다)

lookback 이 자정을 넘으면(예: 전날 22시 음식 → 당일 아침 수면) 그대로 전날 이벤트가 창에
들어온다. `compare.ts` 는 절대 시각(ms)으로 창을 계산하므로 날짜 경계와 무관하다.

> ⚠️ 창을 정확히 채우려면 호출부가 **기간 + 최대 lookback 만큼 앞선 이벤트까지** 넘겨야
> 한다(기간 첫날의 전날 입력을 위해). 그렇지 않으면 첫날들의 창이 잘린다.

## 왜 상관계수를 쓰지 않나

**표본이 작아 반드시 헛것을 본다.** 지금 대부분의 결과는 좋은 날/나쁜 날이 각각 한 자릿수다.
그 위에서 상관계수·p값·신뢰구간·"유의미함"을 계산하면, 우연히 겹친 한두 건이 그럴듯한
숫자로 둔갑한다. 3일 중 3일이 겹쳤다고 상관계수 1.0 을 띄우면 그건 발견이 아니라 착시다.

그래서 계산하는 것은 **단순 빈도뿐**이다: "잘 잔 날 6일 중 5일에 커피가 없었다" 처럼
날짜 수를 세어 나란히 보여주기만 한다. 판단은 사용자가 한다.

- `difference`(good 비율 − bad 비율)는 **정렬용일 뿐 점수가 아니다.** 화면은 이 값으로 factor
  순서를 정할 뿐, "78% 관련" 같은 숫자로 보여주지 않는다.
- 그룹이 5일 미만이면 `enoughData=false` 를 돌려주고, 화면은 비교표 대신
  **"아직 판단하기 이릅니다 (N일)"** 를 보여준다.
- **모르는 날(`unknownDays`, 결과 기록이 없는 날)을 "좋았던 날"에 넣지 않는다.**
  모르는 것과 좋은 것은 다르다.

## presence 결과의 한계 — "없었음"은 "기록되지 않음"을 포함한다

`presence` 결과(craving, digestion 등)에서 "없었던 날(good)"은 **그 증상이 실제로 없었던 날**과
**그날 그냥 말하지 않은 날**을 구분할 방법이 없다. 사용자가 "오늘 갈망 없었음"이라고
따로 기록하지는 않기 때문이다.

그래서 최소한의 방어를 둔다: 매칭 이벤트가 없어도 **그날 기록이 `PRESENCE_GOOD_MIN_EVENTS`
(현재 3)건 이상일 때만 good** 으로 세고, 1~2건이면 `unknown`(판단 보류)으로 돌린다. 기록이
한 건뿐인 날을 "갈망 없던 날"로 세면 `goodDays` 가 부풀려져 비교표가 실제와 반대로 나올 수
있다. 기록이 충분한 날에 안 나타났다면 없었다고 볼 근거가 조금 더 생긴다. (임계값 3은
`compare.ts` 상단 상수 — 실제 데이터를 보고 조정할 값이다)

그래도 이건 완화일 뿐 해결이 아니다. **화면에서도 이 점을 사용자에게 알려야 한다** — 예:
"'없었던 날'에는 그날 기록이 적어 확인되지 않은 날이 섞여 있을 수 있어요." 정직하게
한계를 드러내고, 판단은 사용자에게 맡긴다.

## 원인 후보는 데이터에서 뽑는다

`inputs.ts` 의 `extractInputFactors` 는 원인 후보를 하드코딩하지 않는다. "서리태 두유"를
코드에 박으면 새 음식이 생길 때마다 코드를 고쳐야 한다. 대신:

1. **이름 기반** — food/medication/activity/body_care 의 이름 중 기간에 **2일 이상** 등장한
   것 상위 N개. (body_care 는 name 이 없어 `action_text` 를 식별자로 쓴다)
2. **카테고리 존재 여부** — 각 카테고리가 창 안에 있었나.
3. **수치 기반** — 수면 시간 6h 미만, 그날 식사·간식 3건 이상.

수치 기반의 임계값(6h, 3건)은 **판단이 아니라 표시용 묶음**이다. 사용자별로 기준을 지어내지
않고 널리 쓰는 값을 상수로 두었으며, `inputs.ts` 상단에서 한 곳으로 바꿀 수 있다.
