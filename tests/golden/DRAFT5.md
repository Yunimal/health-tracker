# 골든셋 DRAFT5 — appetite / digestion 카테고리 + v9 버그 3종 (case-031~040)

**근거는 상상이 아니라 실사용 데이터다** — unparsed 최다 항목이 식욕·소화였다. 두 카테고리를
추가하고, 함께 새고 있던 버그 3종(수면 중간 각성·자명한 인과·앞 문장 지시어)을 골든으로 잡는다.

각 발화에 **무엇이 들어있는지 나열만** 했고 파싱 결과(시각 확정·payload 전체)를 흉내내지 않는다.
판단이 갈리는 부분은 **애매한 점**에만 적고 확정하지 않았다 — 확정은 사람이 한다(2단계).

> ⚠️ appetite/digestion payload·중복 규칙·경계는 아직 미확정. 각 case-XXX.json 의 `expected` 는
> 지금 비어 있고(빈 배열), 2단계에서 채운다. 카테고리는 현재 8개(food/mood/sleep/energy/
> menstrual/bowel/medication/activity)에서 **10개**로 늘어난다.

## 추가할 카테고리 (미확정 초안)

### appetite — 배고픔·포만감·식욕 충동

| 필드                | 타입                | 설명                          | 예                   |
| ------------------- | ------------------- | ----------------------------- | -------------------- |
| `kind`              | enum (필수)         | hunger / fullness / craving / no_appetite | —          |
| `intensity_text`    | 원문 표현 또는 null | 강도를 **말한 그대로**        | "너무 배고파", "살짝" |
| `controllable_text` | 원문 표현 또는 null | 참을 수 있는지 원문 그대로    | "참을 만함", "못 참겠음" |
| `note`              | 문자열 또는 null    | 그 밖의 원문                  | —                    |

### digestion — 소화 관련 신체 감각

| 필드             | 타입                | 설명                       | 예                 |
| ---------------- | ------------------- | -------------------------- | ------------------ |
| `kind`           | enum (필수)         | gas / bloating / heartburn / pain / nausea / other | —   |
| `intensity_text` | 원문 표현 또는 null | 강도를 **말한 그대로**     | "심하게", "살짝"   |
| `note`           | 문자열 또는 null    | 그 밖의 원문               | —                  |

## 반드시 지킬 원칙 (사용자 지시)

1. **강도를 숫자로 매기지 않는다.** 원문 표현을 `intensity_text`/`controllable_text` 에 그대로
   보존한다. (activity R18 intensity 와 같은 처리 — mood/energy 의 수치화와 다르다)
2. **판단하는 라벨을 만들지 않는다.** "폭식"·"과식"·"중독" 같은 분류 kind/enum 을 두지 않는다.
   사용자가 그렇게 말했으면 `note` 에 원문으로만 남는다. (CLAUDE.md 원칙 6 — 관찰 도구가
   자책 도구가 되지 않게)
3. **R3(배고픔 → unparsed) 폐기.** 배고픔·식욕·포만감은 이제 appetite 로 간다.
   - 단 **R19 유지**: 섭취 이유로 진술된 배고픔은 `food.reason=hunger`(appetite 이벤트 없음).
   - 경계: **"배고파서 밥 먹었어" → food.reason=hunger** / **"지금 너무 배고파" → appetite** 이벤트.
   - digestion 도입으로 **R15 의 "소화불량·더부룩 → unparsed" 도 폐기** → digestion 으로 간다.
     (bowel=배변 활동 / digestion=소화 감각 구분은 유지)

- `종류`: `fact`(사실 이벤트) / `hypothesis`(추측)
- `카테고리`: appetite / digestion / food / sleep / energy / … / unparsed

> 커버리지: 배고픔 강도 2단계(031) · 참을 수 있는지(032) · 포만감+식욕없음(033) · 섭취 이유
> 배고픔=경계(034) · 가스·더부룩(035) · 속쓰림·위장불편(036) · 소화+음식 공존(037) ·
> 수면 중간 각성=버그(038) · 자명한 인과=버그(039) · 앞 문장 지시어 원인=버그(040).

> recorded_at: 2026-08-19 13:00 KST

| 종류 | 카테고리 | 내용                                       | 시각 | 애매한 점                                       |
| ---- | -------- | ------------------------------------------ | ---- | ----------------------------------------------- |
| fact | food     | 김밥, reason=hunger("배고파서"), 한 줄     | 지금 | **appetite 이벤트를 만들면 안 됨** (R19 유지)   |

> R3 폐기 후 파서가 모든 배고픔을 appetite 로 만들어버리는 과생성이 이 케이스에서 드러난다.

| ---------- | -------- | ----------------------------- | --------- | ---------------------------------------------------------------- |
| fact       | food     | 커피(drink)                   | 어제 오후 | "카페인"은 커피의 성분 — name 을 무엇으로                        |
| fact       | energy   | 졸림, level 낮음              | 오늘      | "하루 종일" 시각 처리                                            |
| hypothesis | —        | cause=**오후 늦게 커피 섭취**, effect=졸림 | —  | **cause_hint 를 앞 문장 내용으로 채운다**                        |

> 🔶 **버그 확인 (v9 프롬프트 규칙):** "그래서 그런지"의 지시어가 **앞 문장(어제 오후 커피)**을

> 원인을 찾아 cause_hint 에 실제 내용을 넣어야 한다.
> **하위 규칙(별도 확인 필요):** 앞 문장에서도 원인을 못 찾으면 hypothesis 를 만들지 말고
> 결과만 fact 로 남긴다(원인 모를 가설은 검증 불가). 이 not-found 변형은 케이스가 더 필요할 수
> 있음 — 2단계에서 040 에 문장 하나 없는 변형을 추가하거나 별도 케이스로 다룰지 결정.

## 2단계에서 확정할 열린 질문 (여기서 정하지 않음)

1. **payload/enum 확정** — appetite(kind 4종) / digestion(kind 6종). `other` 남용 방지 기준.
2. **중복 분리 규칙** — 한 발화의 gas+bloating(035), heartburn+pain(036), fullness+no_appetite(033)
   를 몇 건으로 나눌지. (food R13 / medication R16 처럼 "따로 성립하면 분리" 기준 적용할지)
3. **경계 규칙(R19 vs appetite)** — "배고파서 먹었어"=food.reason / "배고파"=appetite. 프롬프트에
   명시적 경계 예시 필요(034). 과생성(모든 배고픔을 appetite로) 방지가 핵심.
4. **R3 / R15 폐기 반영** — 기존 케이스 재점검: case-001/007(배고픔 unparsed) → appetite 로 바뀜,
   case-018(더부룩 unparsed) → digestion 으로 바뀜. **기존 expected 갱신 필요**(2단계 배치 재파싱).
5. **자명한 인과 규칙(R1 확장)** — "동어반복/정의상 자명한 인과는 hypothesis 로 만들지 않는다"를
   RULES R1 에 추가 + v9 예시. 자명함의 경계(어디까지가 자명한가) 정의.
6. **지시어 원인 규칙** — 앞 문장에서 cause 찾기 / 못 찾으면 hypothesis 없이 결과 fact 만. v9 예시.
7. **수면 각성 규칙** — 중간 각성을 sleep.interruptions/note 로. "요즘/자꾸"(반복 진술)의 시각화.
8. **confidence(R6) 적용** — appetite/digestion 에 amount 개념 없음 → 페널티 없음(activity 처럼).
   precision 페널티만. R6 에 두 카테고리 명시.
9. **스키마/마이그레이션** — events.payload 는 jsonb 라 마이그레이션 불필요(0007 선례). schema.ts
   AppetitePayload/DigestionPayload + index.ts zod + v9 프롬프트 + RULES(R20 appetite / R21
   digestion?) 갱신. 순서: RULES → 프롬프트 → 골든셋 expected (CLAUDE.md 원칙 5).

> 확정 후: RULES(R3/R15 폐기 표시 + appetite/digestion 규칙 + R1 자명인과·지시어원인) → v9 프롬프트
> → case-031~040 expected 채움 → 기존 영향 케이스(001/007/018 등) 갱신 → 배치 재파싱 → test:golden.
